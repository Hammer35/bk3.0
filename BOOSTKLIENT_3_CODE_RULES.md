# BOOSTKLIENT® 3.0 — правила работы с кодом

## 1. Главный принцип

> Каждый тип логики хранится в своём месте.

Нельзя смешивать HTML, CSS, JavaScript, Python, SQL, бизнес-логику, интеграции, фоновые задачи и настройки.

Код должен быть разделён по ответственности, легко находиться и не создавать скрытых зависимостей.

---

## 2. HTML должен быть чистым

В HTML-шаблонах запрещено:
- inline JavaScript;
- большие script-блоки;
- inline CSS;
- style-блоки;
- бизнес-логика;
- сложные вычисления;
- прямые запросы к API;
- SQL;
- секреты;
- дублирование больших фрагментов разметки.

Допустимо:
- Django Template Tags;
- простые условия и циклы;
- HTMX-атрибуты;
- минимальные Alpine.js директивы;
- подключение переиспользуемых компонентов.

---

## 3. Никакого hardcode (жёстко прописанных значений)

Не хардкодить:
- URL;
- API endpoints;
- цвета;
- интерфейсные тексты;
- языки;
- статусы;
- лимиты;
- таймауты;
- роли;
- права;
- пути;
- секреты;
- API keys.

Использовать Django settings, environment variables, constants, enums, конфигурационные модели, design tokens и i18n.

---

## 4. JavaScript

JavaScript хранится отдельно по назначению:

static/js/core/ — HTMX hooks, SSE, CSRF, общие helpers, обработка ошибок.
static/js/components/ — modal, dropdown, tabs, toast, chat panel.
static/js/features/ — strategist, strategy, research, content, approvals, analytics.
static/js/pages/ — только логика, уникальная для конкретной страницы.

JavaScript не должен содержать бизнес-логику, которая должна жить на backend.

---

## 5. Alpine.js

Использовать только для локального UI-состояния:
- показать/скрыть;
- dropdown;
- вкладки;
- modal;
- локальные переключатели.

Не использовать Alpine.js как глобальный state manager (менеджер состояния) и не дублировать в нём backend-логику.

---

## 6. HTMX

HTMX используется для серверной интерактивности.

Принцип:
> Backend является источником истины.

HTMX отправляет запрос, получает HTML-фрагмент и обновляет нужный блок.

---

## 7. CSS

Inline CSS запрещён.

Основные стили создаются через Tailwind CSS, CSS variables и design tokens.

Кастомный CSS хранится логично:
- static/css/tokens.css
- static/css/base.css
- static/css/components/
- static/css/features/

---

## 8. Design Tokens (дизайн-токены)

Повторяющиеся значения должны быть централизованы:
- цвета;
- фоны;
- текст;
- границы;
- отступы;
- радиусы;
- тени;
- длительности анимаций.

Никаких случайных визуальных значений без причины.

---

## 9. Django Apps

Проект разбивается по бизнес-доменам.

Предварительные приложения:
- accounts
- workspaces
- businesses
- pinterest
- strategist
- research
- strategies
- content
- approvals
- scheduler
- publishing
- analytics
- competitors
- recommendations
- notifications

Каждое приложение отвечает только за свой домен.

---

## 10. Никакого god-app

Нельзя складывать весь проект в один core с огромными models.py, views.py и services.py.

Если модуль растёт — он делится по ответственности.

---

## 11. Структура Django-приложения

Рекомендуемые части:
- models/
- views/
- services/
- selectors/
- tasks/
- permissions/
- constants/
- templates/
- static/
- tests/

Маленький модуль может начинаться с отдельных файлов, но при росте должен дробиться.

---

## 12. Views (представления)

View должна:
1. принять запрос;
2. проверить права;
3. провалидировать входные данные;
4. вызвать service;
5. вернуть response.

View не должна содержать длинную бизнес-логику, обращения к нескольким API или сложные workflow.

---

## 13. Services (сервисы)

Бизнес-логика живёт в service layer (слое сервисов).

Сервис отвечает за бизнес-операцию, а не за HTTP.

---

## 14. Selectors (чтение данных)

Сложные запросы к базе отделять от views и сервисов изменения данных.

Это делает код понятнее и упрощает оптимизацию ORM.

---

## 15. Models (модели)

Модели не должны превращаться в файлы на тысячи строк.

В моделях хранить данные, простые инварианты и небольшую доменную логику.

Сложные workflow — в services.

---

## 16. Celery + Valkey

Celery task (фоновая задача) должна быть тонкой оболочкой.

Бизнес-логика должна находиться в сервисе, чтобы её можно было вызвать:
- из Celery;
- из management command;
- из теста;
- вручную.

Valkey используется как брокер, кэш, временное состояние и при необходимости для locks (блокировок).

---

## 17. Интеграции

Все внешние сервисы имеют отдельные clients (клиенты):
- Pinterest;
- OpenAI;
- DeepSeek;
- Telegram;
- MAX;
- другие провайдеры.

Нельзя обращаться к внешнему API напрямую из view.

Направление вызова:
view → service → integration client → external API.

---

## 18. Абстракция LLM (языковой модели)

BOOSTKLIENT® не должен зависеть от одного AI-провайдера.

Нужен общий интерфейс провайдера для:
- generate;
- stream;
- tool calling.

Реализации могут быть OpenAI, DeepSeek, Hermes и другие.

---

## 19. RAG

RAG-логика хранится отдельно от обычной SQL-логики.

Не смешивать в одном месте:
- SQL;
- embeddings;
- vector search;
- prompt building;
- tool calling.

---

## 20. Prompt Management (управление промптами)

Боевые промпты нельзя разбрасывать строками по Python-файлам.

Они должны храниться централизованно и иметь версии.

Например отдельные промпты для:
- system;
- onboarding;
- build strategy;
- update strategy;
- content validation.

---

## 21. Статусы и константы

Не использовать строковые статусы по всему проекту.

Использовать enums / Django choices / constants.

То же касается лимитов, типов задач, ролей и режимов работы.

---

## 22. URL

Все Django URL должны иметь имена.

Нельзя вручную собирать внутренние URL строками.

Использовать reverse() и Django url template tag.

---

## 23. i18n (интернационализация)

Все пользовательские строки переводимы.

Обязательные языки:
- ru
- en

Нельзя жёстко писать русский или английский текст в шаблонах без механизма перевода.

---

## 24. Environment Variables (переменные окружения)

В Git запрещено хранить:
- API keys;
- DB passwords;
- SECRET_KEY;
- Telegram tokens;
- OAuth secrets;
- Pinterest secrets;
- Valkey credentials.

Использовать .env, а в репозитории хранить только .env.example без реальных секретов.

---

## 25. Django settings

Настройки разделять минимум на:
- base;
- development;
- production;
- test.

---

## 26. Logging (логи)

Не использовать print() в production-коде.

Использовать logging и передавать полезный контекст:
- user_id;
- workspace_id;
- business_id;
- task_id;
- request_id.

Не логировать пароли, токены и секреты.

---

## 27. Ошибки

Пользователь не должен видеть traceback или raw API error.

Техническая ошибка идёт в лог, пользователь получает понятное сообщение.

---

## 28. Транзакции

Критические операции выполнять через database transactions:
- публикация;
- изменение статусов;
- списание лимитов;
- массовые операции;
- создание критичных связанных сущностей.

---

## 29. Idempotency (идемпотентность)

Повторный запуск фоновой задачи не должен:
- публиковать Pin дважды;
- списывать лимит дважды;
- создавать дубликаты;
- отправлять одно и то же уведомление бесконечно.

---

## 30. Concurrency (параллельность)

Для конкурентных операций использовать:
- DB constraints;
- select_for_update;
- Valkey locks;
- уникальные ключи идемпотентности.

Особенно для scheduler, publisher, approval и generation buffer.

---

## 31. Миграции

Каждое изменение модели сопровождается Django migration.

Нельзя вручную менять production БД и переписывать уже применённые миграции без крайней необходимости.

---

## 32. Tests (тесты)

Критичная бизнес-логика обязана иметь тесты.

Приоритет:
1. публикация;
2. статусы Pin;
3. permissions;
4. стратегия;
5. approval;
6. scheduler;
7. платежи и лимиты;
8. AI tool calling.

---

## 33. Naming (именование)

Имена должны объяснять назначение.

Запрещены бессмысленные имена вроде:
- temp;
- misc;
- utils2;
- helper_new;
- process2.

Использовать предметные имена: strategy_version, approved_pins, schedule_pin, build_strategy.

---

## 34. Magic Numbers (магические числа)

Числовые и строковые пороги должны иметь понятные имена и централизованные настройки.

---

## 35. Размер функций

Функция выполняет одну понятную задачу.

Большие функции с множеством вложенных условий должны разделяться.

---

## 36. DRY без фанатизма

Не дублировать бизнес-логику.

Но читаемость важнее преждевременной универсализации.

---

## 37. Dependencies (зависимости)

Перед добавлением новой библиотеки проверить:
1. можно ли решить стандартными средствами;
2. поддерживается ли библиотека;
3. насколько она тяжёлая;
4. какие зависимости она добавляет;
5. нет ли известных проблем безопасности.

---

## 38. Производительность frontend

Не подключать глобально JS/CSS, который нужен только одной странице.

Использовать lazy loading, page-specific assets и загрузку по необходимости.

---

## 39. Медиа

Изображения и видео должны быть оптимизированы.

Не загружать огромный оригинал для маленького превью.

Использовать thumbnails, современные форматы и lazy loading.

---

## 40. Комментарии

Комментарий объясняет почему принято решение, а не пересказывает очевидный код.

---

## 41. Документация

Сложные модули должны иметь README или docstring:
- назначение;
- вход;
- выход;
- зависимости;
- основные сценарии.

Особенно: strategist, scheduler, publisher, analytics, RAG и integrations.

---

## 42. Git

Основная ветка: main.

Для разработки использовать feature branches, например:
- feature/ai-strategist;
- feature/pinterest-oauth;
- feature/approval-telegram.

---

## 43. Commits (коммиты)

Один коммит — одна логическая задача.

Сообщение коммита должно объяснять изменение.

---

## 44. Code Review (проверка кода)

Перед merge проверять:
- архитектуру;
- безопасность;
- тесты;
- миграции;
- i18n;
- hardcode;
- permissions;
- производительность;
- возможные конфликты.

---

## 45. Security (безопасность)

Frontend никогда не считается доверенным.

Backend всегда проверяет:
- permissions;
- ownership;
- workspace;
- business;
- account;
- limits;
- допустимость действия.

---

## 46. Multi-Tenant Safety (изоляция пользователей)

Каждый пользователь должен видеть и изменять только доступные ему данные.

Особенно это касается:
- Pinterest accounts;
- strategies;
- analytics;
- pins;
- products;
- competitors.

---

## 47. Разделение ответственности

Примеры:
- scheduler не генерирует изображения;
- content не публикует напрямую в Pinterest;
- analytics не меняет стратегию напрямую;
- strategist не выполняет сырой SQL;
- Telegram integration не меняет статусы в обход approval service.

---

## 48. Dependency Direction (направление зависимостей)

Высокоуровневая бизнес-логика не зависит напрямую от конкретного внешнего API.

Использовать интерфейсы/адаптеры, чтобы провайдера можно было заменить.

---

## 49. Single Source of Truth (единый источник истины)

Для каждого типа данных должен быть один главный источник.

Примеры:
- статус Pin хранится в БД;
- Telegram только вызывает backend-действие;
- стратегия хранится в Strategy Engine;
- frontend не хранит отдельную копию бизнес-состояния как источник истины.

---

## 50. Feature Flags (флаги функций)

Экспериментальные возможности включаются через feature flags или permissions.

Не делать скрытые исключения по email или user_id в коде.

---

## 51. Производительность backend

Перед добавлением сложной логики проверять:
- можно ли сократить количество SQL-запросов;
- можно ли кэшировать;
- нужно ли вынести операцию в Celery;
- можно ли вернуть промежуточный результат;
- нужны ли все данные прямо сейчас.

---

## 52. Контроль N+1 запросов

В Django ORM использовать select_related, prefetch_related, annotate и aggregation там, где это необходимо.

Не допускать N+1 в списках и таблицах.

---

## 53. Кэш

Кэшировать только то, что имеет смысл:
- тяжёлые исследования;
- справочники;
- агрегированную аналитику;
- редко меняющиеся результаты.

Кэш не заменяет корректную модель данных.

---

## 54. Правило перед созданием новой функции

Перед написанием кода определить:
1. к какому домену относится функция;
2. где хранятся данные;
3. кто источник истины;
4. какие сервисы вызываются;
5. нужна ли Celery-задача;
6. нужны ли permissions;
7. нужны ли переводы;
8. нужны ли тесты;
9. нужен ли новый UI-компонент;
10. как функция влияет на производительность.

---

## 55. Главный критерий качества

Новый разработчик должен быстро понять:
- где находится нужный код;
- какой модуль за что отвечает;
- как изменить одну функцию без поломки другой;
- как протестировать изменение;
- как заменить интеграцию;
- как добавить функциональность без переписывания проекта.

> Чистая архитектура важнее быстрого хаотичного результата.

---

## 56. Valkey compatibility rule (правило совместимости Valkey)

Valkey является выбранным broker/cache для проекта.

До production необходимо подтвердить совместимость Celery 5.6 + Valkey 8.1.x отдельным интеграционным тестом.

Если несовместимость обнаружена:
1. не возвращаться автоматически на Redis;
2. не менять базовый стек без решения;
3. рассмотреть RabbitMQ как broker для Celery;
4. оставить Valkey как cache/locks, если это целесообразно;
5. зафиксировать новое решение в матрице стека.


---

## 57. Надёжность Celery + Valkey

Главный принцип:

> Celery доставляет задачу, но истинное состояние операции хранится в PostgreSQL.

И второй принцип:

> Любая критичная задача должна безопасно переживать повторный запуск.

Обязательные правила:

- критичные задачи должны быть idempotent (идемпотентными);
- для важных задач использовать late acknowledgement, где это оправдано;
- аварийная потеря worker не должна приводить к тихой потере задачи;
- retry (повторы) использовать только для временных ошибок;
- применять exponential backoff (увеличивающуюся задержку между повторами);
- после исчерпания retry задача получает FAILED и сохраняется для разбора;
- разделять очереди по назначению;
- критичная публикация не должна ждать за массовой генерацией;
- использовать отдельные workers для разных типов очередей;
- visibility timeout должен быть больше максимального времени выполнения задачи;
- использовать soft/hard time limits;
- состояние операции фиксировать в PostgreSQL;
- для критичных операций использовать unique job key / lock;
- worker должен завершаться graceful shutdown (корректно завершать текущую работу);
- отслеживать очередь, retry, failed, время выполнения и состояние workers.

Рекомендуемые очереди:

- critical — публикации и критичные операции;
- generation — генерация контента;
- research — исследования;
- analytics — аналитика;
- notifications — Telegram / MAX;
- low_priority — некритичные фоновые задачи.

Для публикации Pin использовать состояние в БД, например:

READY → PUBLISHING → PUBLISHED

Если worker упал на PUBLISHING, система должна уметь определить зависшее состояние и безопасно восстановить операцию.
