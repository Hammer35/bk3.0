# Делегирование для экономии лимита Codex

## Роли

- **Codex — руководитель.** Понимает запрос владельца, определяет границы задачи, выбирает исполнителя, выдаёт поручение, принимает результат и отвечает владельцу.
- **Исполнитель — OpenCode с выбранной моделью.** Выполняет поручение в согласованных файлах и возвращает краткий отчёт с доказательствами.
- OpenRouter — провайдер моделей, OpenCode — агент, который может использовать эти модели. Они не взаимозаменяемы. Прямые вызовы OpenRouter API и поручение агенту OpenCode — разные способы работы.
- Владелец подтвердил: поручения выполняет OpenCode, связь только через файлы в `.kilo/agent-state/`. HTTP-API OpenCode и прямые вызовы OpenRouter API для этой схемы не использовать.

## Полномочия Codex

Владелец поручил Codex принимать все решения по выполнению поставленной задачи после проверки фактов и результатов. OpenCode предлагает варианты и выполняет поручения; его выводы становятся основанием для действий только после приёмки Codex. В пределах согласованной задачи Codex самостоятельно выбирает способ реализации, распределение работы, доработки и принимает либо отклоняет результат. Обычные технические решения не возвращать владельцу на согласование. Если требуется выйти за пределы задачи или ранее разрешённых расходов и действий, уточнить только недостающее разрешение.

## Решение перед каждой задачей

1. Прочитать `LOG.md`, `HANDOFF.md` и реестр `agent.sh list`.
2. Оценить сложность, объём работы, цену ошибки и затраты на передачу контекста и приёмку.
3. По умолчанию поручать исполнителю ограниченные работы: поиск по заданной области, сбор фактов, документацию, локальные исправления с ясными требованиями, запрошенные проверки.
4. Codex оставляет себе постановку задачи, архитектурные решения, неоднозначную диагностику, разрешение конфликтов и итоговую приёмку. Однострочную правку дешевле сделать самому, если поручение и проверка потребуют больше работы.
5. Коротко сообщить решение: что делегируется, кому и что проверит Codex. Не обещать экономию в процентах без измерений.

## Как выдать поручение

Создать `TASK-<id>.md` в этой папке после `claim`. Записать в `LOG.md` имя исполнителя и путь поручения через `agent.sh note codex "..."`.

Обязательные поля поручения:

```text
ID / статус: предложено | принято | выполняется | готово | доработка | заблокировано | принято Codex
Исполнитель / модель: фактический идентификатор либо пока не выбран
Цель: наблюдаемый результат
Контекст: только нужные факты, пути и решения
Разрешённые файлы: точные пути или ограниченная область поиска
Ограничения: что нельзя менять, внешние вызовы и бюджет
Критерии приёмки: конкретные признаки готовности
Проверки: только необходимые и разрешённые владельцем
Результат: путь RESULT-<id>.md
```

Исполнитель подтверждает принятие в `LOG.md`, занимает файлы своим именем до правки и обновляет статус. Запись поручения не означает, что агент запущен. Без подтверждения задача остаётся предложенной; Codex не сообщает о выполнении или фоновой работе.

## Экономия

- Передавать короткое поручение и ссылки на точные файлы, а не весь диалог или репозиторий.
- Не повторять работу исполнителя: Codex смотрит изменённый участок, результат и существенные доказательства.
- Объединять близкие мелкие задания, если у них одни требования и область файлов.
- Начинать с самой экономичной доступной модели, пригодность которой подтверждена для этого вида работы. Бесплатный каталог не доказывает качество или возможность успешного вызова.
- Не переключать модель Codex и не выбирать платную модель исполнителя без нужного разрешения. Ранее выданное разрешение учитывать в его пределах; разрешение на GigaChat не переносить автоматически на OpenRouter.
- Не запускать бесконечные попытки. После неудачи определить причину; одна адресная доработка, затем Codex пересматривает способ выполнения. При тайм-ауте платный запрос автоматически не повторять.
- Секреты, `.env`, ключи и пароли не передавать в поручениях или отчётах.

## Приёмка

Исполнитель возвращает в `RESULT-<id>.md`: результат, изменённые пути, выполненные проверки с фактическим исходом, оставшиеся проблемы, модель и доступные показатели расхода.

Codex проверяет соответствие запросу, существенный diff, отсутствие чужих изменений и доказательства проверок. При необходимости запрашивает адресную доработку. Непроверенное явно обозначает. Ответ исполнителя не считается автоматически верным.

В `LOG.md` фиксировать итог каждой делегированной задачи: ID, вид работы, исполнитель/модель, принято или доработка, число попыток, известные токены/стоимость, объём приёмки Codex. Если расход неизвестен, писать «неизвестен», а не вычислять его из длины ответа. При следующих задачах использовать результаты этого журнала для выбора исполнителя.

## Общий репозиторий

- В командах задавать `export AGENT_NAME=codex` или имя исполнителя. Не менять общий `git config agent.name`.
- Перед правкой использовать `agent.sh claim`; при конфликте не трогать чужие файлы.
- Перед каждой новой задачей и при получении результата перечитать `LOG.md`.
- Коммиты и публикация — только в рамках разрешения владельца. Не коммитить в `main`, не использовать `git add -A`, не обходить хук.
- После завершения работы обновить `HANDOFF.md` и освободить файлы. Если предстоит согласованный коммит, держать их занятыми до коммита.
