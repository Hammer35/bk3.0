# BOOSTKLIENT® 3.0 — Design System (дизайн-система)

## Статус документа

Живой документ.

Задача: зафиксировать правила интерфейса BOOSTKLIENT® 3.0 до начала активной разработки, чтобы MVP сразу создавался как часть боевого продукта и не требовал полной переделки при масштабировании.

---

# 1. Главный принцип интерфейса

BOOSTKLIENT® 3.0 — не набор разрозненных страниц.

Это единая Pinterest-экосистема, где пользователь проходит путь:

**Обучение → Исследование → Стратегия → Контент → Планирование → Публикация → Аналитика → Улучшение → Масштабирование**

Интерфейс должен поддерживать этот путь и создавать ощущение единой рабочей среды.

Главный принцип:

> Один каркас приложения, который постепенно наполняется новыми модулями.

MVP не должен иметь временный интерфейс.

MVP должен использовать тот же каркас и те же компоненты, которые останутся в production (боевой версии).

---

# 2. Основная архитектура интерфейса

Приложение строится вокруг четырёх постоянных зон:

## 2.1. Sidebar (левое меню)

Постоянная основная навигация.

Предварительные разделы:

1. Главная
2. Обучение
3. Мой бизнес
4. Исследование
5. Стратегия
6. Контент
7. Контент-план
8. Очередь
9. Публикации
10. Аналитика
11. Конкуренты
12. Рекомендации
13. Автопилот
14. Настройки

На этапе MVP реально работают:

- Мой бизнес
- ИИ-стратег
- Стратегия

Остальные разделы могут:
- быть скрыты;
- быть disabled (недоступны);
- иметь статус «Скоро».

Не создавать для MVP другую навигацию.

---

## 2.2. Topbar (верхняя панель)

Содержит глобальные элементы:

- текущий Workspace (рабочее пространство);
- текущий Business (бизнес);
- текущий Pinterest Account (Pinterest-аккаунт);
- глобальный поиск;
- уведомления;
- статус фоновых задач;
- профиль пользователя.

Topbar не должен перегружаться.

---

## 2.3. Main Workspace (основная рабочая область)

Здесь отображаются:

- страницы;
- таблицы;
- карточки;
- стратегия;
- аналитика;
- контент;
- результаты исследований.

Главная рабочая зона должна иметь единый максимальный размер и предсказуемую сетку.

---

## 2.4. AI Strategist Layer (слой ИИ-стратега)

ИИ-стратег — не отдельный случайный чат.

Он должен быть постоянной частью интерфейса.

Варианты отображения:

- боковая панель;
- плавающая кнопка;
- полноэкранный режим чата;
- контекстная панель внутри конкретного раздела.

ИИ должен понимать, в каком разделе находится пользователь.

Пример:

Если пользователь находится в «Стратегии» и пишет:

> Убери это направление.

ИИ должен понимать контекст текущей стратегии, а не просить пользователя объяснять всё заново.

---

# 3. Основная продуктовая модель навигации

Навигация должна отражать логику продукта, а не техническую структуру backend (серверной части).

Пользователь должен видеть задачи, а не внутренние механизмы.

Плохо:

- Parsers
- Jobs
- Workers
- Generation API

Хорошо:

- Исследование
- Стратегия
- Контент
- Очередь
- Аналитика

---

# 4. MVP Interface (интерфейс первой версии)

MVP должен включать полноценный production shell (боевой каркас интерфейса).

Минимальный набор экранов:

## 4.1. Authentication (вход и регистрация)

- вход;
- регистрация;
- восстановление доступа.

---

## 4.2. ИИ-стратег

Главный рабочий экран первой версии.

Функции:

- диалог;
- отображение этапа диагностики;
- запрос сайта;
- вопросы по бизнесу;
- подтверждение автоматически найденной информации;
- запуск исследования;
- отображение прогресса;
- выдача стратегии;
- обсуждение стратегии;
- изменение стратегии.

---

## 4.3. Business Profile (профиль бизнеса)

Отображает:

- название;
- сайт;
- нишу;
- поднишу;
- рынок;
- язык;
- аудиторию;
- цели;
- категории товаров;
- Pinterest-аккаунты;
- ограничения;
- текущую стратегию.

---

## 4.4. Strategy (стратегия)

Отдельный структурированный экран.

Не хранить стратегию только внутри чата.

Стратегия должна быть самостоятельным объектом интерфейса.

Блоки:

- цель;
- рынок;
- аудитория;
- приоритетные направления;
- ключевые слова;
- рекомендуемые доски;
- типы контента;
- частота публикаций;
- сезонность;
- план 30 / 60 / 90 дней.

Действия:

- Принять
- Изменить
- Обсудить с ИИ
- Создать новую версию
- Посмотреть историю изменений

---

# 5. Design System (дизайн-система)

Все страницы строятся из ограниченного набора переиспользуемых компонентов.

Запрещено создавать уникальный стиль для каждого экрана.

# 7. Иерархия кнопок

Минимум три уровня:

## Primary (главная)

Для ключевого действия страницы.

Пример:
- Принять стратегию
- Запустить исследование
- Создать контент

На одном экране желательно одна доминирующая Primary-кнопка.

## Secondary (вторичная)

Пример:
- Изменить
- Сохранить черновик
- Открыть подробнее

## Tertiary / Ghost (дополнительная)

Пример:
- Отмена
- Скрыть
- Ещё

Опасные действия должны иметь отдельный destructive (опасный) стиль.

---

# 8. Состояния интерфейса

Каждый модуль обязан проектироваться минимум для следующих состояний:

1. Empty (нет данных)
2. Loading (загрузка)
3. Processing (обработка)
4. Success (успешно)
5. Partial Success (частичный результат)
6. Error (ошибка)
7. No Access (нет доступа)
8. Disabled (недоступно)
9. Waiting Approval (ждёт подтверждения)
10. Background Task (задача выполняется в фоне)

Нельзя проектировать только «идеальное заполненное состояние».

---

# 9. Фоновые процессы

BOOSTKLIENT® будет выполнять большое количество длительных операций:

- исследование ниши;
- анализ конкурентов;
- генерация контента;
- проверка контента;
- аналитика;
- перестроение стратегии.

Интерфейс не должен блокироваться.

Пользователь должен видеть:

- что запущено;
- текущий статус;
- что уже готово;
- что можно делать параллельно;
- когда результат появился.

Не использовать интерфейс, где пользователь вынужден смотреть на один spinner (индикатор загрузки) несколько минут.

---

# 10. Progressive Disclosure (постепенное раскрытие сложности)

BOOSTKLIENT® будет сложной системой.

Новичку нельзя показывать всё сразу.

Принцип:

> Сначала только то, что нужно сейчас. Детали раскрываются по мере необходимости.

Пример:

Вместо 50 показателей исследования сначала:

- 5 главных выводов;
- рекомендуемое действие.

Кнопка:

**Посмотреть подробное исследование**

---

# 11. ИИ-стратег как часть UX

ИИ не должен постоянно выдавать длинные полотна текста.

Предпочтительная структура ответа:

1. Короткий вывод.
2. Что найдено.
3. Что предлагается сделать.
4. Конкретное действие.

Пример:

> Нашёл 3 перспективных направления.
>
> Сильнее всего растёт «small bedroom ideas».
>
> Предлагаю добавить это направление в стратегию.
>
> [Добавить] [Посмотреть данные]

ИИ должен уметь выдавать UI Actions (действия интерфейса), а не только текст.

---

# 12. Контекстные действия

Все ключевые объекты должны иметь действия рядом с собой.

Пример keyword (ключевого слова):

- добавить в стратегию;
- исключить;
- посмотреть тренд;
- найти конкурентов;
- создать контент.

Пример Pin (пина):

- одобрить;
- отклонить;
- переделать;
- изменить текст;
- изменить изображение;
- посмотреть причину создания.

---

# 13. Responsive (адаптивность)

Основной приоритет:

**Desktop First (сначала десктоп)**

Причина:
BOOSTKLIENT® — рабочий инструмент с таблицами, исследованиями, стратегией и аналитикой.

Обязательные уровни:

## Desktop
Полный функционал.

## Tablet
Основные функции без потери критичных возможностей.

## Mobile
Не пытаться переносить весь desktop-интерфейс.

На мобильном приоритет:

- ИИ-стратег;
- уведомления;
- одобрение контента;
- ключевые показатели;
- быстрые действия.

---

# 14. Telegram / MAX и мобильный UX

Telegram и MAX рассматриваются как внешние интерфейсы управления.

Они не заменяют веб-приложение.

Используются для:

- уведомлений;
- одобрения пинов;
- отклонения;
- запроса переделки;
- подтверждения ежедневной очереди;
- критичных предупреждений.

Все данные и реальные статусы хранятся в BOOSTKLIENT®.

---

# 15. Layout Grid (сетка)

Точные значения будут определены позже после выбора визуального направления.

На архитектурном уровне принять:

- единая система отступов;
- единая ширина контейнеров;
- единая сетка карточек;
- фиксированные правила sidebar;
- одинаковые вертикальные ритмы.

Не использовать случайные значения отступов на разных страницах.

---

# 16. Spacing System (система отступов)

Использовать ограниченную шкалу.

Предварительный принцип:

**4 / 8 / 12 / 16 / 24 / 32 / 48 / 64**

Все основные отступы должны браться из этой шкалы.

---

# 17. Typography (типографика)

На первом этапе не фиксируем конкретное семейство шрифта до выбора визуального направления.

Но фиксируем уровни:

- Display
- H1
- H2
- H3
- Body
- Body Small
- Caption
- Label
- Code / Technical

Не использовать произвольные размеры текста.

---

# 18. Color System (цветовая система)

До отдельного визуального этапа не фиксируем конкретные HEX-цвета.

Но система должна включать семантические токены:

- Background
- Surface
- Surface Elevated
- Text Primary
- Text Secondary
- Border
- Primary
- Primary Hover
- Success
- Warning
- Error
- Info
- Disabled

Компоненты должны использовать токены, а не прямые цвета.

Это позволит позже менять визуальное оформление без переписывания компонентов.

---

# 19. Light / Dark Mode

Архитектура компонентов должна позволять поддержку:

- Light Mode (светлая тема)
- Dark Mode (тёмная тема)

Даже если в MVP будет реализована только одна тема.

Цвета нельзя жёстко прописывать внутри компонентов.

---

# 20. Design Tokens (дизайн-токены)

Сразу использовать токены для:

- цветов;
- размеров;
- радиусов;
- теней;
- отступов;
- типографики;
- z-index;
- длительности анимаций.

Это позволит централизованно менять стиль продукта.

---

# 21. Tables (таблицы)

Таблицы будут одним из главных элементов продукта.

Должны поддерживать:

- сортировку;
- фильтры;
- поиск;
- выбор строк;
- массовые действия;
- скрытие колонок;
- сохранённые представления;
- пагинацию или виртуализацию;
- адаптацию под большие объёмы данных.

Не создавать отдельную реализацию таблицы для каждого раздела.

---

# 22. Cards (карточки)

Использовать для:

- метрик;
- рекомендаций;
- результатов исследования;
- стратегических направлений;
- товаров;
- пинов.

Карточки должны иметь единые правила:

- заголовок;
- основной контент;
- статус;
- действия;
- дополнительная информация.

---

# 23. AI Approval UX (одобрение ИИ-действий)

Разделить действия ИИ по уровню риска.

## Low Risk (низкий риск)

Можно выполнять автоматически.

Пример:
- открыть данные;
- отфильтровать таблицу;
- подготовить черновик.

## Medium Risk (средний риск)

Показать изменение перед применением.

Пример:
- изменить стратегию;
- изменить контент-план.

## High Risk (высокий риск)

Требовать явного подтверждения.

Пример:
- массовая публикация;
- удаление;
- включение автопилота;
- изменение лимитов;
- подключение внешнего аккаунта.

---

# 24. История изменений

Стратегии, настройки и критичные действия ИИ должны иметь историю.

Пользователь должен понимать:

- что изменилось;
- когда;
- кто изменил;
- почему;
- можно ли откатить.

---

# 25. Accessibility (доступность)

На базовом уровне:

- достаточный контраст;
- keyboard navigation (управление клавиатурой);
- focus states (состояния фокуса);
- подписи у иконок;
- понятные ошибки форм;
- не полагаться только на цвет для передачи состояния.

---

# 26. Performance UX (восприятие скорости)

Интерфейс должен ощущаться быстрым даже при длительных фоновых процессах.

Использовать:

- skeletons (каркасы загрузки);
- optimistic UI (оптимистичное обновление интерфейса) там, где безопасно;
- фоновые задачи;
- промежуточные результаты;
- кэширование;
- lazy loading (ленивая загрузка);
- виртуализацию больших списков.

---

# 27. Правило разработки компонентов

Перед созданием нового UI-компонента разработчик должен проверить:

1. Есть ли уже такой компонент?
2. Можно ли расширить существующий?
3. Нужно ли добавлять новый вариант в дизайн-систему?
4. Используются ли токены?

Запрещено плодить визуально похожие, но технически разные компоненты без причины.

---

# 28. Предварительная структура frontend (клиентской части)

Рекомендуемый принцип:

- App Shell
- Pages
- Features
- Entities
- Shared UI
- Design Tokens
- AI Components

Конкретный frontend framework (фреймворк интерфейса) будет выбран отдельно.

---

# 29. Что фиксируем сейчас, а что позже

## Фиксируем сейчас

- архитектуру приложения;
- навигацию;
- основные зоны;
- набор базовых компонентов;
- состояния;
- правила ИИ-интерфейса;
- адаптивность;
- токены;
- принципы UX.

## Определяем позже

- точный логотип;
- конкретные HEX-цвета;
- конкретный шрифт;
- финальные радиусы;
- финальные тени;
- графический стиль;
- иллюстрации;
- декоративные элементы.

Сначала архитектура и UX, затем визуальный стиль.

---

# 30. Главный критерий дизайн-системы

После MVP не должно возникнуть задачи:

> Перерисовать всё приложение заново.

Правильный сценарий:

> Добавить в существующий каркас новые модули и компоненты.

---

# 31. Следующий этап разработки дизайн-системы

Нужно последовательно определить:

1. App Shell (каркас приложения)
2. Sidebar (левое меню)
3. Topbar (верхняя панель)
4. AI Strategist UI (интерфейс ИИ-стратега)
5. Business Profile (профиль бизнеса)
6. Strategy Page (страница стратегии)
7. таблицы
8. карточки
9. система статусов
10. формы
11. модальные окна
12. визуальный язык
13. цветовую систему
14. типографику
15. адаптивность

После этого можно собирать первые экраны MVP без риска построить временный интерфейс.


# 32. Обязательные темы интерфейса

BOOSTKLIENT® 3.0 должен иметь две полноценные темы:

- **Light Theme (светлая тема)**
- **Dark Theme (тёмная тема)**

Обе темы являются обязательными для production (боевой версии), а не дополнительной функцией.

Требования:

- все компоненты используют semantic tokens (семантические токены), а не жёстко заданные цвета;
- контраст и читаемость должны сохраняться в обеих темах;
- таблицы, формы, карточки, модальные окна и ИИ-чат должны одинаково корректно работать в обеих темах;
- тема пользователя сохраняется в настройках;
- желательно поддержать системную тему устройства как значение по умолчанию.

---

# 33. Многоязычность

BOOSTKLIENT® 3.0 должен быть многоязычным с первого этапа разработки.

Обязательные языки:

- **Русский**
- **English (английский)**

Архитектура интерфейса должна быть построена через i18n (интернационализацию), а не через вручную зашитые строки.

Требования:

- весь UI-текст хранится в словарях переводов;
- кнопки, статусы, ошибки, подсказки, системные сообщения и onboarding (первичное знакомство) должны переводиться;
- пользователь может переключать язык без потери состояния;
- выбранный язык сохраняется в профиле;
- тексты ИИ-стратега должны генерироваться на языке пользователя;
- нельзя проектировать компоненты только под длину русского или только английского текста;
- учитывать, что длина подписей и кнопок в разных языках отличается.

Главный критерий:

Для BOOSTKLIENT® 3.0 выбран следующий базовый стек.

- **Django**

---

## Frontend (клиентская часть)

### Django Templates (шаблоны Django)

Основная HTML-разметка приложения строится сервером через Django Templates.

Причина:
- меньше отдельного frontend-кода;
- меньше JavaScript;
- быстрее первая загрузка;
- проще поддержка;
- единый проект без разделения на отдельный frontend и backend.

---

### HTMX

Используется для динамических обновлений интерфейса без полной перезагрузки страницы.

Примеры:
- обновление частей стратегии;
- фильтрация таблиц;
- загрузка результатов исследования;
- подтверждение действий;
- изменение статусов;
- подгрузка контента;
- работа модальных окон и форм.

Главный принцип:
сервер возвращает готовые HTML-фрагменты, а не требует обязательной JSON-обвязки и отдельного frontend-state (состояния клиентского приложения).

---

### Alpine.js

Используется только для лёгкой локальной интерактивности в браузере.

Примеры:
- раскрывающиеся меню;
- вкладки;
- локальные переключатели;
- небольшие модальные состояния;
- client-side (клиентские) UI-состояния.

Alpine.js не должен превращаться в отдельный frontend-framework (фреймворк интерфейса).

---

### Tailwind CSS

Используется как основа дизайн-системы и стилизации интерфейса.

Задачи:
- сетка;
- отступы;
- темы;
- типографика;
- состояния;
- компоненты;
- адаптивность.

Все визуальные решения должны опираться на design tokens (дизайн-токены) и семантические классы.

# 56. Valkey вместо Redis — лицензионное решение

**Valkey 8.1.x**

Перед production обязательна отдельная compatibility test (проверка совместимости):

- Python 3.12;

- Kombu;
- Python redis client;
- reconnect / retry;
- TLS при необходимости;
- visibility timeout;
- broker persistence;
- worker restart;
- lost connection recovery.

До прохождения этого теста Valkey считается архитектурно выбранным, но не production-validated (не подтверждённым для боевой эксплуатации).

# 57. Tailwind CSS — дисциплина дизайн-системы

Tailwind является основным инструментом стилизации BOOSTKLIENT® 3.0, но используется внутри единой дизайн-системы.

Обязательные правила:

- utility-классы Tailwind разрешены в шаблонах;
- inline CSS запрещён;
- визуальные значения строятся через design tokens;
- arbitrary values (произвольные значения) используются только как редкое исключение;
- повторяемые UI-паттерны оформляются как переиспользуемые компоненты;
- одинаковые компоненты не должны иметь случайно отличающиеся цвета, радиусы и отступы;
- светлая и тёмная темы используют один набор компонентов;
- Tailwind configuration / CSS variables являются централизованным источником визуальных токенов.

Принцип:

> Utility-first не означает «каждый экран оформляется заново».

Дизайн-система определяет правила, Tailwind только реализует их.
