# BOOSTKLIENT® 3.0 — архитектура ИИ

## Статус документа

Живой документ.

Цель: зафиксировать архитектуру AI Strategist (ИИ-стратега), правила доступа к данным, память, RAG, провайдеров моделей, fallback и выполнение действий.

Главные принципы:

> LLM получает только минимально необходимый контекст.

> Секреты, токены и критичные персональные данные не отправляются в LLM.

> Любое действие ИИ проходит независимую backend-проверку.

---

# 1. Роль ИИ-стратега

ИИ-стратег не является источником истины и не хранит бизнес-состояние сам по себе.

Его задачи:
- вести диалог;
- понимать намерение пользователя;
- собирать недостающие данные;
- запрашивать нужный контекст;
- анализировать данные;
- формировать рекомендации;
- строить и изменять стратегию;
- вызывать инструменты BOOSTKLIENT®;
- объяснять результаты;
- предлагать следующие действия.

---

# 2. Источники истины

Источник истины по бизнес-данным:
**PostgreSQL**

Источник знаний:
**RAG (поиск по базе знаний)**

Источник временного контекста:
**Memory (память)**

LLM:
- не считается базой данных;
- не считается источником прав доступа;
- не считается источником фактов о текущем состоянии системы.

---

# 3. Архитектура потока данных

User / Business Data
↓
Context Builder (сборщик контекста)
↓
Policy Layer (слой правил доступа к данным)
↓
Memory / RAG / Analytics
↓
LLM Provider
↓
Tool Call
↓
Backend Validation
↓
Action

---

# 4. Context Builder (сборщик контекста)

Context Builder определяет, какие данные нужны модели для конкретной задачи.

LLM не получает весь аккаунт пользователя автоматически.

Пример:

Запрос:
> Почему упали переходы?

Контекст может включать:
- агрегированную аналитику за нужный период;
- текущую стратегию;
- несколько лучших и худших Pin;
- ключевые слова;
- последние значимые изменения.

Контекст не должен включать весь архив данных без необходимости.

---

# 5. Минимизация контекста

Правило:
> Передавать модели только данные, которые реально нужны для текущего ответа или действия.

Преимущества:
- быстрее ответы;
- ниже стоимость;
- меньше риск утечки;
- меньше шум;
- меньше вероятность ошибочного вывода.

---

# 6. Data Classification (классификация данных)

Данные разделяются минимум на три категории.

## Public (публичные)
- публичные ключевые слова;
- публичные Pinterest данные;
- открытые данные конкурентов;
- общие правила Pinterest.

Могут передаваться LLM.

## Internal (внутренние)
- стратегия;
- контент-план;
- агрегированная аналитика;
- внутренние рекомендации;
- состояние кампаний.

Могут передаваться LLM только в рамках доступного пользователю Business / Workspace.

## Sensitive (чувствительные)
- пароли;
- OAuth access token;
- refresh token;
- API keys;
- SECRET_KEY;
- платёжные данные;
- сессионные cookies;
- внутренние секреты;
- приватные credentials.

Sensitive-данные в LLM не отправляются.

---

# 7. Персональные данные

Персональные данные пользователя должны передаваться модели только если это необходимо для функции.

По умолчанию минимизировать:
- email;
- имя;
- телефон;
- внутренние IDs;
- IP;
- платёжные данные.

Если данные не нужны модели — они не передаются.

---

# 8. Business Memory (память бизнеса)

Память делится на типы.

## Profile Memory
Стабильные факты:
- ниша;
- рынок;
- язык;
- аудитория;
- товары;
- цели;
- ограничения.

## Working Memory
Текущее состояние:
- активная стратегия;
- активные кампании;
- приоритеты;
- текущая интенсивность публикаций;
- активные доски.

## Decision History
История решений:
- что изменили;
- почему изменили;
- на основании каких данных;
- кто подтвердил изменение;
- какой результат получили.

---

# 9. Память не равна истории чата

Нельзя использовать всю историю чата как постоянную память.

Из диалога извлекаются структурированные факты и решения.

Полный chat log хранится отдельно и не подмешивается в каждый запрос.

---

# 10. Chat History Retention (срок хранения истории чата)

Полный chat log должен иметь ограниченный срок хранения.

Точный срок будет определён отдельно с учётом:
- продукта;
- требований приватности;
- стоимости хранения;
- юридических требований.

Decision History и Business Memory могут храниться дольше, если это нужно продукту.

---

# 11. RAG

RAG используется для знаний, а не для текущего состояния бизнеса.

Начальный набор курируемых материалов и evaluation examples хранится в `docs/ai-knowledge/`. Состав и назначение корпуса описаны в его `README.md`; правила ответа остаются системной политикой, а примеры — evaluation-набором, не retrieval-контентом.

Первый рабочий контур RAG расположен в `apps/knowledge/`: индексатор читает только утверждённые глобальные Markdown-документы, строит смысловые фрагменты с overlap, сохраняет GigaChat embeddings вместе с provenance в PostgreSQL и выбирает контекст по cosine similarity. Запрос пользователя получает embedding только при наличии проиндексированных фрагментов. Команда `index_knowledge` по умолчанию делает сухой прогон без API; платный запрос выполняется только с флагом `--embed`. Версия индексатора участвует в решении о повторной индексации. Текущие параметры и ограничения описаны в `docs/ai-knowledge/README.md`.

В RAG могут находиться:
- правила Pinterest;
- обучающие материалы;
- внутренние методики;
- инструкции BOOSTKLIENT®;
- документы по стратегии;
- проверенные best practices;
- накопленные знания продукта.

## Подготовка фрагментов для поиска

- Сначала сохранять структуру источника: документ, заголовки, разделы, абзацы и ссылки. Резать текст по смысловым границам, а не только через равные символьные интервалы.
- Использовать настраиваемое перекрытие (overlap) соседних фрагментов: часть текста предыдущего чанка повторяется в следующем. Это помогает не терять определение, условие или вывод, если смысл проходит через границу чанка.
- Не переносить overlap через несвязанные разделы и границы документов. Размер задавать в токенах и выбирать по типу материала на контрольных вопросах; универсальное значение заранее не фиксировать.
- Сохранять для каждого чанка документ, версию, заголовок/раздел, диапазон исходного текста, язык, дату и область доступа. Перекрытые фрагменты должны оставаться привязаны к тем же исходным координатам.
- При поиске объединять или удалять почти дублирующиеся перекрытые результаты, чтобы не тратить контекст модели на повтор одного и того же текста и оставить место для независимых свидетельств.

Overlap может улучшить полноту найденного контекста, но сам по себе не гарантирует правильность ответа. Её проверяют на наборе реальных вопросов: нашёлся ли нужный фрагмент, достаточно ли исходного контекста, верно ли ответ сослался на источник.

---

# 12. RAG Scope (область доступа)

Каждый RAG-запрос обязан учитывать scope:
- global knowledge;
- workspace;
- business;
- user-private data.

Нельзя допустить, чтобы RAG одного пользователя возвращал данные другого.

---

# 13. RAG и удаление данных

Если пользователь удаляет Business / Workspace, нужно удалить или отвязать:
- документы;
- embeddings;
- векторные записи;
- memory records;
- chat history;
- AI job metadata;
- связанные индексы.

Удаление только SQL-записи недостаточно.

---

# 14. LLM Provider Abstraction

BOOSTKLIENT® не должен зависеть от одного AI-провайдера.

Общий интерфейс:
- generate();
- stream();
- tool_call();
- structured_output();
- embeddings() при необходимости.

Возможные реализации:
- OpenAIProvider;
- DeepSeekProvider;
- HermesProvider;
- другие.

---

# 15. Provider Contract (контракт провайдера)

Каждый провайдер должен возвращать унифицированный результат.

Бизнес-логика не должна знать:
- формат конкретного SDK;
- специфические поля ответа;
- внутренние ошибки API.

Провайдер адаптирует это к единому формату BOOSTKLIENT®.

---

# 16. Model Router (маршрутизатор моделей)

Разные задачи могут использовать разные модели.

Примеры:

## Простые задачи
- классификация;
- краткое резюме;
- формирование короткого текста.

Использовать быструю дешёвую модель.

## Сложные задачи
- стратегия;
- анализ конкурентов;
- перестройка плана;
- сложные объяснения.

Использовать более сильную модель.

---

# 17. Fallback (резервирование)

Если основной AI-провайдер недоступен:

Возможные сценарии:
- retry;
- переключение на резервного провайдера;
- постановка задачи в очередь;
- возврат пользователю статуса «временно недоступно».

Критичное правило:
> Резервная модель не должна тихо менять поведение системы без логирования.

Любое переключение провайдера логируется.

---

# 18. Provider Failure Policy

Ошибки делятся на:

## Temporary
- timeout;
- network error;
- 5xx;
- rate limit.

Допускается retry / fallback.

## Permanent
- invalid API key;
- unsupported model;
- invalid request;
- permission error.

Не повторять бесконечно.

---

# 19. Tool Calling

LLM может предложить вызвать инструмент.

Но выполнение происходит только через backend.

Пример:
LLM → publish_content()

Backend обязан проверить:
- ownership;
- permissions;
- status;
- approval;
- limits;
- account state;
- idempotency.

---

# 20. Risk Levels для AI Tools

## Low Risk
- поиск;
- чтение;
- фильтрация;
- подготовка черновика.

Можно выполнять автоматически.

## Medium Risk
- изменение стратегии;
- изменение контент-плана;
- изменение очереди.

Нужен preview / confirmation.

## High Risk
- публикация;
- массовое удаление;
- включение автопилота;
- изменение прав;
- отключение аккаунта.

Требуется явное подтверждение пользователя. Каждый пин одобряется отдельным действием для конкретной версии. ИИ не создаёт одобрение вместо пользователя; разрешения Pinterest не отменяют это правило.

---

# 21. Prompt Injection Protection

Внешние данные считаются недоверенными.

Особенно:
- страницы сайтов;
- описания товаров;
- конкурентный контент;
- документы;
- сообщения внешних источников.

Внешний текст не имеет права изменять system rules.

---

# 22. Разделение ролей в prompt

Не смешивать:
- system instructions;
- user request;
- external context.

Внешние данные должны передаваться как данные, а не как инструкции.

---

# 23. Prompt Management

Промпты должны:
- храниться централизованно;
- иметь версии;
- иметь назначение;
- иметь тесты;
- иметь changelog при критичных изменениях.

Нельзя разбрасывать production prompts по случайным Python-файлам.

---

# 24. Structured Outputs (структурированные ответы)

Для бизнес-логики предпочтительны структурированные ответы.

Примеры:
- JSON schema;
- typed objects;
- строго заданные поля.

Не использовать свободный текст там, где система ожидает машинно-обрабатываемый результат.

---

# 25. Validation структурированного ответа

Любой структурированный ответ LLM проходит:
- schema validation;
- business validation;
- permission validation;
- sanity checks.

Проверяется соответствие профилю бизнеса, исходным данным и ограничениям пользователя. Фактические утверждения должны иметь проверяемые источники; гипотезы и недостаток данных обозначаются явно. Проверка не предсказывает успех пина в алгоритмах Pinterest. Наблюдаемые метрики не считаются доказательством причин результата. Не выдавать предполагаемую причину изменения метрик за установленный факт.

LLM output не считается автоматически корректным.

---

# 26. AI Job State

Долгие AI-задачи должны иметь статус в PostgreSQL.

Примеры:
- PENDING;
- RUNNING;
- WAITING_INPUT;
- COMPLETED;
- FAILED;
- CANCELLED.

Celery/Valkey не является единственным источником состояния AI-задачи.

---

# 27. AI Cost Control (контроль стоимости)

Для каждого типа задачи нужно учитывать:
- provider;
- model;
- input tokens;
- output tokens;
- количество вызовов;
- стоимость;
- retry cost;
- fallback cost.

Эти данные должны логироваться и агрегироваться.

---

# 28. User / Workspace Limits

Позже должны быть определены лимиты:
- стратегии;
- AI requests;
- generation;
- research;
- validation;
- re-generation.

Лимиты должны проверяться backend, а не LLM.

---

# 29. Кэширование AI-результатов

Если результат можно безопасно переиспользовать, допускается кэш.

Примеры:
- одинаковый анализ публичной темы;
- неизменившаяся справочная информация;
- повторный запрос одного и того же документа.

Не кэшировать чувствительные персональные данные без ясной политики.

---

# 30. AI Observability (наблюдаемость ИИ)

Логировать:
- provider;
- model;
- task type;
- latency;
- token usage;
- cost;
- retry;
- fallback;
- tool calls;
- errors.

Не логировать секреты.

---

# 31. Privacy by Design

Перед любой новой AI-функцией задавать:
1. Какие данные нужны модели?
2. Можно ли передать меньше?
3. Нужно ли вообще отправлять эти данные внешнему провайдеру?
4. Можно ли агрегировать?
5. Можно ли обезличить?

---

# 32. Удаление данных пользователя

При удалении пользователя / бизнеса нужно учитывать:
- Business Memory;
- Working Memory;
- Decision History;
- chat logs;
- RAG docs;
- embeddings;
- AI jobs;
- provider-side stored data, если провайдер что-то хранит согласно контракту.

---

# 33. Provider Data Policy

Перед подключением AI-провайдера необходимо отдельно проверить:
- хранит ли он запросы;
- использует ли их для обучения;
- срок хранения;
- регион обработки;
- наличие opt-out;
- условия для API / business customers.

Эта проверка обязательна до production.

---

# 34. AI Security

ИИ не может:
- повышать себе права;
- обходить permissions;
- менять ownership;
- раскрывать чужие данные;
- выполнять опасные действия без подтверждения;
- читать secrets;
- самостоятельно выбирать себе доступ к новым данным.

---

# 35. Failure UX

Если AI недоступен, интерфейс должен оставаться рабочим.

Пользователь должен получить:
- понятный статус;
- возможность повторить;
- сохранение уже введённых данных;
- отсутствие потери прогресса.

---

# 36. Главный принцип архитектуры

> ИИ — интеллектуальный слой над продуктом, а не сам продуктовый backend.

BOOSTKLIENT® должен продолжать хранить данные, права, статусы и действия независимо от конкретной модели.

---

# 37. Pinterest AI Compliance

Pinterest Materials/API data нельзя использовать для training / fine-tuning моделей без явного письменного разрешения Pinterest.

Разрешённый по умолчанию подход BOOSTKLIENT®:

- inference only (разовый анализ);
- минимальный контекст;
- отсутствие обучения на Pinterest API data;
- отсутствие сохранения Pinterest data у AI-провайдера дольше необходимого, если это можно контролировать;
- явное логирование источника данных.

Если Pinterest data используется как transient context для LLM, этот use case должен быть раскрыт Pinterest при Standard access review и при необходимости отдельно письменно подтверждён.


# 38. Контракт ответов диалогового MVP

Этот контракт относится к текущему текстовому чату со стратегом. Базовый поиск RAG по утверждённым глобальным документам подключён; BusinessMemory, Context Builder бизнес-состояния и инструменты пока не подключены.

## 38.1 Что модель получает

В текущей реализации запрос собирается из:

1. системного prompt, сформированного из актуальной записи Business в PostgreSQL;
2. до 12 последних сообщений текущей AIConversation из PostgreSQL;
3. найденные фрагменты глобального RAG с метаданными и ссылками на источники, если retrieval вернул подходящие материалы;
4. выбранный GigaChat provider/model.

Текущая реализация не добавляет результаты Pinterest API, исследование веба, BusinessMemory или вызовы инструментов. Глобальный RAG по одобренным документам работает, но не сообщает данные аккаунта, сайта, рынка или конкурентов. Не утверждать, что стратег проверил их, если отдельный источник данных этого не подтверждает.

Источники и назначение хранилищ:

| Данные | Источник истины | Передача модели | Статус |
|---|---|---|---|
| Профиль бизнеса и его цели | `Business` в PostgreSQL | Поля, нужные системному prompt | Работает |
| История сообщений | `AIConversation` / `AIMessage` в PostgreSQL | Последние 12 сообщений | Работает; это контекст диалога, не долговременная память |
| Стратегия | `Strategy` / `StrategyVersion` в PostgreSQL | Показывается пользователю; в prompt чата не добавляется | Работает: черновик из подтверждённого профиля, версии, основания с manifest источников, правка и явное подтверждение (владелец/админ/редактор) |
| Контент-план | `ContentPlan` / `ContentPlanItem` в PostgreSQL | Показывается пользователю; в prompt чата не добавляется | Работает: идеи на 4 недели из подтверждённой версии стратегии (направление, доска, ключ обязаны существовать в версии), черновик → подтверждение; пины не создаются, ничего не публикуется |
| Пины (черновики текста) | `Pin` / `PinVersion` в PostgreSQL | Генерация по пункту подтверждённого контент-плана; тексты пользователю, не в prompt чата | Работает: заголовок, описание, alt text, ссылка; 12 проверок с вердиктами `pass` / `review` / `block` и статусом `not_checked`, одна повторная попытка при блокировке; изображений нет, публикации нет; одобрение (`Approval`) — только на веб-странице «Пины», по конкретной версии, отдельным действием человека |
| Товары, доски, Pins и метрики | Доменные записи PostgreSQL | Только через явно реализованный Context Builder | Для текущего чата не подключено |
| Подтверждённая память о бизнесе и решениях | `BusinessMemory` в PostgreSQL | Факты (только сообщённые пользователем) — в системный prompt и черновик стратегии с ref `memory:<id>`; решения в prompt не попадают | Работает: команды «Запомни:», «Забудь:», «Что ты помнишь?», до 50 фактов, отказ для паролей/ключей/платёжных и личных данных, решения о стратегии записываются с причиной и автором; удаляется вместе с бизнесом |
| Методики и проверенные внешние знания | Управляемый корпус знаний + индекс поиска | Только найденные фрагменты с источниками | Работает базовый global RAG по утверждённым русскоязычным документам; tenant-specific знания не подключены |
| Ответ модели и usage | `AIMessage` в PostgreSQL | Не применимо | Ответ, provider/model и token usage сохраняются; снимок полного prompt/context не сохраняется |

PostgreSQL остаётся источником истины для состояния бизнеса. Векторный индекс, если он будет выбран для RAG, является производным поисковым индексом, а не заменой бизнес-таблиц или оригинальных документов.

## 38.2 Как отвечать при недостатке данных

- Факт из профиля или сообщения пользователя можно повторять как сообщённый пользователем факт, указывая источник словами, если это важно для смысла.
- Не выводить нишу, ассортимент, аудиторию, бюджет, результаты или ограничения из общих ожиданий о Pinterest и выдавать вывод за факт о конкретном бизнесе.
- Если необходимого факта нет, он неполный или противоречивый, задать один короткий уточняющий вопрос до персональной рекомендации.
- Общий совет можно дать без персонализации, явно назвав его общим подходом, и отдельно указав, каких данных не хватает для адаптации.
- Числа, нормы частоты публикаций, сроки и ожидаемые результаты требуют проверяемого источника и области применимости. Без этого не выдавать конкретное число за отраслевую норму; допустимо предложить его только как проверяемую гипотезу, обозначив это пользователю.
- Не заявлять, что факт «проверен», если не приложен реально использованный источник. Для изменчивых фактов источник должен включать дату проверки.
- При конфликте сначала назвать конфликтующие сведения и спросить, какое из них актуально; не выбирать молча.

Пример: если пользователь только создал аккаунт и сообщил, что у него нет досок и стратегии, это не раскрывает его нишу или аудиторию. Сначала спросить про продукт/категорию и целевого покупателя. Не подменять ответ данными профиля продавцов маркетплейсов, если именно такой профиль не передан в текущий контекст.

## 38.3 Финальный ответ и внутреннее рассуждение

Пользователю показывается только финальный ответ модели. Скрытые рассуждения, chain-of-thought, внутренние черновики и анализ выбора ответа не запрашивать, не сохранять и не отображать.

Когда объяснение полезно, показывать краткое проверяемое обоснование: использованные факты, их источник, допущения и оставшуюся неопределённость. Такое объяснение — часть финального ответа, а не трассировка внутренних рассуждений модели.

Текущий провайдерский адаптер получает и сохраняет `message.content`; отдельный канал reasoning в коде не обрабатывается. Поэтому многословный или нумерованный ответ сам по себе не является показом reasoning. Его качество определяется соблюдением правил выше и наличием подтверждений для утверждений.

## 38.4 Происхождение данных и аудит запроса

При развитии Context Builder каждый включённый фрагмент контекста должен иметь внутреннюю запись происхождения: тип источника, идентификатор записи/документа, поле или фрагмент, дату актуальности и признак подтверждения. Для RAG также сохранять версию документа и диапазон/якорь цитируемого фрагмента.

Для аудита AIMessage должны быть доступны версия prompt, provider/model, token usage и manifest использованных источников. Полный текст персонального контекста не дублировать в логах без необходимости. Если для воспроизводимости понадобится snapshot prompt, определить для него срок хранения, доступ и удаление вместе с политикой удаления бизнеса.

Сейчас в AIMessage сохраняются provider/model/token usage, версия prompt (`prompt_version`: версия шаблона и хеш точного собранного prompt) и manifest источников (`context_manifest`: виды и идентификаторы данных, без самого текста: поля профиля, id фактов памяти, число сообщений истории, документы базы знаний, ресурсы Pinterest API, id/ref источников стратегии). Версии шаблонов закреплены отпечатками в `apps/strategist/provenance.py`; тест падает, если текст prompt изменён без новой версии. Полный текст prompt по-прежнему не сохраняется. Поэтому исторический запрос можно реконструировать лишь частично: запись профиля могла измениться после ответа, а использованный prompt snapshot не сохранён.

## 38.5 Порядок реализации

1. Базовый контракт ответа и RAG подключены: профиль Business, недавняя история, найденные глобальные фрагменты, ссылки, антиспам-правила и ограничения сообщества. Это не означает, что модельный отказ является backend-валидацией.
2. Следующий шаг — ввести версионирование prompt и полный регрессионный контур: нейтральные вопросы, нехватка/конфликт фактов, запрещённый контент, эвфемизмы, prompt injection и ссылки на фактически найденные источники.
3. Реализовать Context Builder с manifest источников каждого запроса; до этого явно ограничивать выводы теми данными, которые действительно доступны чату.
4. Спроектировать BusinessMemory отдельно от истории переписки: подтверждённые факты и решения с provenance, временем обновления и удалением.
5. Для первой генерации Pin сделать черновой сценарий с серверной проверкой по актуальным правилам `pass`/`review`/`block`; не подключать публикацию, пока нет проверок аккаунта, URL, разрешённого инструмента и явного одобрения.
6. Подключать исследовательские источники и действия через отдельные адаптеры, backend authorization, аудит и подтверждения риска.

Критерий готовности диалогового MVP: тесты подтверждают, что ассистент не выдаёт отсутствующие сведения за профиль пользователя, запрашивает недостающие данные, маркирует гипотезы, не выдумывает количественные нормы и не показывает внутренние рассуждения.
