# BOOSTKLIENT® 3.0 — Performance Budgets (бюджеты производительности)

## Статус документа

Живой документ.

Цель: зафиксировать численные и архитектурные ограничения производительности, чтобы BOOSTKLIENT® 3.0 оставался быстрым, лёгким и предсказуемым по мере роста.

Главный принцип:
> Скорость и доступ к информации важнее декоративной сложности.

---

# 1. Классы операций

## Fast Path (быстрый путь)
Цель: до 300–500 мс.

Примеры:
- открыть обычную страницу;
- получить небольшую таблицу;
- изменить простой статус;
- сохранить простую форму.

## Interactive (интерактивный)
Цель: до 1–2 секунд.

Примеры:
- фильтрация;
- пересчёт небольшого блока;
- подгрузка фрагмента через HTMX;
- небольшая аналитическая выборка.

## Background (фоновый)
Если операция стабильно занимает несколько секунд и больше, её нужно рассматривать как фоновую.

Примеры:
- анализ сайта;
- генерация Pin;
- массовая проверка;
- исследование ниши;
- крупная аналитика.

## Long-running (длительный)
Выполняется только через Celery с сохранением статуса и прогресса.

---

# 2. TTFB

TTFB (время до первого байта) для обычных страниц:
целевой ориентир — менее 500 мс.

Это не абсолютная гарантия для всех страниц, но превышение должно быть объяснимо.

---

# 3. Backend Response Time

Для обычных синхронных запросов без тяжёлой логики:
целевой ориентир — 300–500 мс.

Если операция часто превышает 1–2 секунды:
- оптимизировать;
- кэшировать;
- разбить на этапы;
- или вынести в Celery.

---

# 4. JavaScript Budget

Для обычной рабочей страницы:
ориентир — до 150–200 KB после gzip/brotli.

Правила:
- не грузить JS, который не нужен текущей странице;
- избегать тяжёлых UI-библиотек;
- Alpine.js использовать точечно;
- HTMX не дублировать собственным клиентским state manager.

---

# 5. CSS Budget

Ориентир для собранного CSS:
до ~100 KB после минификации и сжатия.

Правила:
- Tailwind content scanning должен быть корректно настроен;
- не тащить неиспользуемые стили;
- повторяемые компоненты строить системно;
- избегать нескольких параллельных CSS-фреймворков.

---

# 6. HTML

Первичная HTML-разметка должна быть минимально необходимой.

Не рендерить скрытые тяжёлые блоки заранее, если их можно подгрузить по запросу.

---

# 7. Изображения

Для первого экрана:
- ориентир 200–300 KB на отдельное изображение;
- использовать WebP/AVIF, если подходит;
- использовать responsive sizes;
- не отдавать оригинал большого разрешения для маленького превью.

Ниже первого экрана:
- lazy loading обязателен.

---

# 8. Видео

Видео не должно блокировать первый рендер.

Требования:
- poster обязателен;
- autoplay только если не ухудшает скорость;
- muted по умолчанию;
- lazy loading;
- mobile может получать статичное изображение вместо видео.

---

# 9. Таблицы

Нельзя рендерить тысячи строк сразу.

Использовать:
- pagination;
- server-side filtering;
- server-side sorting;
- virtualisation при реальной необходимости.

Для больших таблиц число SQL-запросов должно контролироваться.

---

# 10. ORM и SQL

Перед merge сложных списков проверить:
- N+1;
- select_related;
- prefetch_related;
- annotate;
- indexes;
- количество SQL-запросов;
- latency запросов.

---

# 11. Аналитика

Тяжёлые агрегаты не должны пересчитываться на каждый page load.

Использовать:
- background aggregation;
- caching;
- precomputed daily metrics;
- snapshots.

---

# 12. AI Context

Не отправлять модели весь аккаунт пользователя.

Использовать Context Builder.

Ограничивать:
- размер контекста;
- количество исторических сообщений;
- дублирующиеся данные;
- повторные запросы к неизменившимся источникам.

---

# 13. AI Latency

Потоковый ответ через SSE должен начинаться как можно раньше.

Для долгих AI-задач:
- показывать progress;
- сохранять промежуточный статус;
- не блокировать интерфейс.

---

# 14. Celery Threshold

Операция должна уходить в Celery, если:
- может занять больше нескольких секунд;
- зависит от медленного внешнего API;
- может потребовать retry;
- может быть ресурсоёмкой;
- должна продолжиться после ухода пользователя со страницы.

---

# 15. Cache

Кэшировать:
- тяжёлые исследования;
- повторные справочные данные;
- агрегированную аналитику;
- редко меняющиеся результаты.

Не кэшировать бездумно критичное состояние.

---

# 16. Media Lifecycle

Временные файлы не должны бесконтрольно занимать диск.

Использовать TTL и автоматическую очистку через Celery Beat.

---

# 17. Page-specific Assets

Не подключать глобально JavaScript или CSS, который нужен только одному экрану.

Использовать page-specific assets и lazy loading.

---

# 18. Производительность новых функций

Перед merge новой тяжёлой функции проверить:
- вырос ли JS bundle;
- вырос ли CSS;
- изменился ли TTFB;
- выросло ли количество SQL-запросов;
- появились ли N+1;
- выросло ли время HTMX-ответов;
- появилась ли синхронная тяжёлая логика;
- нужна ли Celery.

---

# 19. Регрессия

Новая функция не должна заметно ухудшать ключевые экраны без отдельного архитектурного решения.

Если ухудшение оправдано, оно должно быть зафиксировано и измерено.

---

# 20. Performance Monitoring

Мониторинг должен собирать минимум:
- request latency;
- slow endpoints;
- slow SQL;
- Celery task duration;
- queue age;
- AI latency;
- external API latency;
- disk usage;
- media growth.

---

# 21. Staging Performance Check

Перед production release на staging проверить:
- основные страницы;
- основные HTMX-сценарии;
- массовую генерацию;
- Celery queues;
- публикацию;
- AI streaming;
- таблицы;
- media loading.

---

# 22. Mobile

Mobile версия должна быть легче desktop.

Не загружать тяжёлые элементы, которые пользователь не может полноценно использовать на мобильном.

---

# 23. Лендинг

Для маркетинговой страницы приоритет:
- быстрое отображение основного текста;
- лёгкие реальные скриншоты;
- ленивые изображения ниже первого экрана;
- отсутствие тяжёлых декоративных библиотек;
- видео только при контролируемом весе.

---

# 24. Главный критерий

> Пользователь не должен ждать тяжёлую операцию в заблокированном интерфейсе, если её можно выполнять в фоне.

---

# 25. Второй критерий

> Производительность считается частью функциональности продукта, а не косметической оптимизацией после релиза.
