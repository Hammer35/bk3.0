# Пины из изображений — логика генерации

Статус: проект, 10 октября 2026. Код ещё не написан.

Сейчас пин в 3.0 рождается из текста: пункт контент-плана → текст → изображение прикладывается потом. Этот документ описывает второй вход, где отправная точка — изображение. Источников изображений два:

1. **Свои фото** — пользователь загружает файлы.
2. **Маркетплейс** — фото из карточки WB (позже Etsy, Ozon).

Оба источника сходятся в один конвейер. Разница между ними — только в том, откуда берутся факты о товаре и что считается главным.

Образец — 2.0 (`batch_generate_pin_content_task` для своих фото, `wb_generate_and_queue_task` для маркетплейсов). Берём из неё порядок этапов, но не транспорт и не модели.

## 1. Принципы

- **Модель сменная.** GigaChat сейчас тестовый. Новый код вызывает интерфейс, а не `GigaChatProvider` напрямую (см. раздел 6).
- **Факты важнее описания фото.** Для маркетплейса правда — карточка. Описание фото добавляет только видимое: цвет, сцену, человека, способ ношения. Свойства, которых нет в карточке (материал, размер, состав, скидка), текст не утверждает.
- **Фото храним у себя.** Ссылки маркетплейсов умирают, а WB режет запросы. Фото копируется в базу при получении и дальше живёт как `PinImage`.
- **Ключи подбираются автоматически.** Пользователь ключи не вводит, но может посмотреть, откуда они взялись.
- **Ничего не публикуется само.** Конец конвейера — черновик пина, который ждёт одобрения человеком, как сейчас.
- **Fail closed.** Если какой-то этап не сработал, пин не притворяется готовым: он уходит на оценку человека (`REVIEW`) с понятной причиной или не создаётся.

## 2. Новые сущности

| Модель | Назначение |
| --- | --- |
| `Product` | Товар бизнеса: площадка (`UPLOAD`/`WB`/`ETSY`/`OZON`), артикул, ссылка, название, бренд, категория, факты карточки (JSON), когда прочитан. Для своих фото — то, что ввёл пользователь. |
| `ImageAsset` | Исходное фото: байты, `sha256` (уникален в пределах бизнеса), размеры, источник и исходный URL, `product` (может быть пустым), описание фото (JSON) и модель, которая его дала. |

Изменения существующих моделей:

- `Pin.plan_item` становится необязательным, добавляется `Pin.asset` → `ImageAsset`. Ограничение в базе: у пина есть пункт плана **или** фото (или оба, если фото подобрали под пункт плана).
- `WBImageAnalysis` обобщается в кэш описаний по `sha256` для любого источника. Повторно одно и то же фото не описываем и не платим.
- `AIJob.Kind` пополняется `PIN_FROM_IMAGES`.

## 3. Конвейер (общий для обоих источников)

Одна фоновая задача `AIJob` на пачку фото. Прогресс и ошибки — в `AIJob.notes`, как у текущей генерации.

### Этап 0. Факты о товаре

- **Маркетплейс:** читаем карточку (`wb_products`). Берём название, бренд, категорию, характеристики, описание продавца. Это главный источник.
- **Свои фото:** короткая форма при загрузке — «что за товар» (обязательно) и «куда ведёт пин» (ссылка, необязательна). Если ссылка ведёт на карточку WB, факты подтягиваются из карточки автоматически, и пин считается «маркетплейсным» по правилам фактов.
- Без фактов и без названия товара конвейер не запускается.

### Этап 1. Отбор фото

- **Маркетплейс:** берём все фото карточки и отсеиваем:
  - уже использованные (тот же `sha256` в пине, который не отклонён);
  - мелкие (короче 600 px по меньшей стороне);
  - точные и визуально близкие дубли.
- При сравнении между разными карточками сохранять артикул и цвет: одна композиция с разным цветом товара означает низкое разнообразие, но сама по себе не основание автоматически исключать отдельную карточку. Фирменный стиль учитывать отдельно. Помечать сходные кадры и предлагать выбор или разнесение публикаций; это редакционная оценка, а не прогноз решения модерации Pinterest. Примеры — `docs/ai-knowledge/examples/wb-image-similarity-2026-11-08.md`.
- **Свои фото:** все загруженные файлы проходят `process_upload` (проверка, перекодирование). Дубли по `sha256` пропускаются с сообщением.
- Оставшиеся кандидаты оцениваются после визуального описания (этап 2), затем сортируются по баллу. Для одежды и украшений фото на человеке может получить более высокую оценку, но это не обязательное условие.
- Автоматически отбираются не более N фото на товар (настройка, по умолчанию 6). Если прошедших порог меньше, список не дополняется слабыми кандидатами.
- **Первичные пороги:** 80–100 — выбрать автоматически; 60–79 — показать на ручную проверку; ниже 60 — не включать автоматически. Пользователь может вручную выбрать технически пригодное фото из нижних баллов. Жёсткие пропуски вручную не возвращаются.
- **Жёсткий пропуск:** файл не читается, меньшая сторона меньше 600 px, дубль/уже использованное фото, товар явно не тот или не виден, либо изображение непригодно технически.
- **Формат пина (решение владельца 23.10.2026):** фото масштабируется по узкой стороне до 1000 px, высота пропорциональна, без обрезки и полей. Фото WB 900×1200 → 1000×1333.

### Этап 2. Описание фото (VisionModel)

Модель возвращает строгий JSON, без свободного текста:

```json
{
  "subject": "что главное на фото",
  "visible": ["предметы и детали, которые видно"],
  "colors": ["основные цвета"],
  "setting": "фон/сцена: студия, интерьер, улица",
  "product_match": "MATCH | UNCERTAIN | MISMATCH",
  "visibility": "MAIN | SECONDARY | PARTIAL | NONE",
  "technical_quality": "GOOD | ACCEPTABLE | POOR | UNUSABLE",
  "composition": "STRONG | ACCEPTABLE | WEAK",
  "category_fit": "STRONG | ACCEPTABLE | WEAK",
  "person": true,
  "wears_product": true,
  "text_on_image": "надписи, если есть",
  "flags": ["watermark", "collage", "text_heavy", "low_quality"]
}
```

- Ответ проверяется по схеме. Если JSON не прошёл проверку — одна повторная попытка, затем «фото не описано».
- Описание фото сопоставляется с названием, категорией и доступными фактами товара. В ответе используются только перечисления; числовой рейтинг вычисляет код, не модель.
- `MATCH` означает визуально совместимый с товаром предмет; свойства вроде состава и материала подтверждаются только фактами карточки. `MAIN` — товар главный и хорошо различим; `SECONDARY` — различим, но не главный; `PARTIAL` — частично закрыт или обрезан; `NONE` — неразличим. `GOOD` — чёткий и достаточно освещённый кадр; `ACCEPTABLE` — мелкие недостатки; `POOR` — заметное размытие, шум или плохой свет; `UNUSABLE` — товар нельзя рассмотреть. Композиция и пригодность для категории оцениваются по видимости товара и уместности сцены для этого типа товара.
- **Рейтинг из 100 баллов:**

  | Признак | Значения и баллы |
  | --- | --- |
  | Соответствие товару (35) | `MATCH` — 35; `UNCERTAIN` — 15; `MISMATCH` — жёсткий пропуск |
  | Видимость товара (25) | `MAIN` — 25; `SECONDARY` — 18; `PARTIAL` — 8; `NONE` — жёсткий пропуск |
  | Техническое качество (20) | `GOOD` — 20; `ACCEPTABLE` — 15; `POOR` — 6; `UNUSABLE` — жёсткий пропуск |
  | Композиция (10) | `STRONG` — 10; `ACCEPTABLE` — 7; `WEAK` — 3 |
  | Пригодность для категории (10) | `STRONG` — 10; `ACCEPTABLE` — 7; `WEAK` — 3 |

- `product_match=UNCERTAIN`, любой флаг качества и неуспешный анализ запрещают автоотбор и отправляют технически пригодное фото на ручную проверку.
- Флаги `watermark`, `collage` и `text_heavy` сами по себе не означают отказ: фото получает предупреждение и не выбирается автоматически.
- Дополнительного вызова модели для рейтинга нет: перечисления возвращаются вместе с описанием фото в том же запросе. Балл вычисляется кодом.
- Балл сортирует только автоматический выбор; причину балла и флаги показываем рядом с фото. Начальные пороги 80/60 нужно проверить на размеченной выборке своих товаров до расширения автоматического отбора.
- Фото не описано:
  - маркетплейс — продолжаем на фактах карточки, пин получает замечание `REVIEW` «фото не проверено моделью»;
  - свои фото — продолжаем на названии товара, тоже с `REVIEW`.
- Описание кэшируется по `sha256`.

### Этап 3. Ключевые слова — автоматически

Основа — существующий `research_pin_keywords` (сейчас вызывается только из чата):
корни из названия товара → реальные фразы Pinterest Trends → отбор моделью → наборы по 2–3 фразы, в каждом есть хотя бы одна товарная.

Что добавляем:

1. **Источник корней:** название товара, категория и `subject` из описания фото (для своих фото без карточки это главный источник).
2. **Слияние со стратегией:** ключевые фразы подтверждённой стратегии и контент-плана тоже идут в кандидаты, с пометкой источника.
3. **Распределение по фото:** каждый пин получает свой набор (`_pin_sets`). Набор подбирается под фото: фото на человеке → фразы про образ/стиль; предмет на фоне → товарные фразы; интерьер → фразы про применение. Один набор не повторяется в пачке.
4. **Кэш:** исследование кэшируется на товар и день (уже так, 6 часов), поэтому 6 фото одного товара — одно исследование.
5. **Нет данных Pinterest** (аккаунт не подключён, передача данных выключена, API упал): берём фразы стратегии, пин получает `REVIEW` «ключи не из Pinterest». Выдумывать ключи моделью без источника нельзя.

У каждого ключа в версии пина хранится источник: Pinterest Trends / стратегия / контент-план.

### Этап 4. Привязка к стратегии

- Набор ключей сопоставляется с пунктами подтверждённого контент-плана и досками стратегии. Совпадение по ключевой фразе или направлению — пин получает доску и направление этого пункта.
- Совпадения нет — доска из настроек генерации (`GenerationPreset`). Доску модель не придумывает.
- Нет подтверждённой стратегии — генерация из фото всё равно работает, но доска берётся только из настроек.

### Этап 5. Текст

Расширяем текущую генерацию (`pin_generation`). На вход модели идут:

- факты товара (с пометкой «единственный источник свойств»);
- описание фото (с пометкой «только видимое»);
- набор ключей пина;
- угол подачи и стиль заголовка — ротация по пачке, как в 2.0 (вопрос, список, как сделать, утверждение…);
- последние 30 заголовков бизнеса — не повторять;
- язык и ограничения длины (`pin_text_limits`).

Один вызов на пин плюс одна повторная попытка с причинами блокировки — как сейчас.

### Этап 6. Проверки

Все существующие 12 проверок `pin_checks`, плюс новые:

| Проверка | Что ловит | Вердикт |
| --- | --- | --- |
| `facts_only` | Текст называет свойство, которого нет в фактах карточки (материал, размер, состав, цена) | BLOCK для маркетплейса |
| `photo_match` | Текст называет цвет или предмет, которого нет ни в описании фото, ни в фактах | REVIEW |
| `image_quality` | Флаги фото: водяной знак, коллаж, много текста, плохое качество | REVIEW |
| `image_ratio` | Пропорции не 2:3 (`ratio_note`, уже есть) | REVIEW, с подсказкой |
| `keywords_source` | Ключи не из Pinterest | REVIEW |

### Этап 7. Сохранение

Создаём `Pin` (с `asset`, и с `plan_item`, если нашли пункт плана), `PinVersion` с текстом, проверками и происхождением и `PinImage` — копию фото. Статус — «Ждёт одобрения» или «Требуется переделка», как сейчас. В `PinVersion.generation` пишем:

- модели (текст и описание фото) и их токены;
- источник фактов;
- источник каждого ключа;
- угол подачи;
- `sha256` фото.

## 4. Чем отличаются два источника

| | Свои фото | Маркетплейс |
| --- | --- | --- |
| Главный источник | Описание фото + название от пользователя | Факты карточки |
| Описание фото | Определяет содержание | Добавляет только видимое |
| Отбор фото | Все загруженные, кроме дублей | Лучшие из карточки, без использованных |
| Ссылка | Из формы (может не быть) | Карточка товара |
| Корни ключей | Название + `subject` фото | Название + категория карточки |
| `facts_only` | Только если ссылка на карточку WB | Всегда |

## 5. Порядок реализации

1. **Основа:** интерфейс моделей (раздел 6), `Product`, `ImageAsset`, общий кэш описаний, VisionModel на GigaChat, `Pin.plan_item` необязательный. Миграция вместе с моделями.
2. **Свои фото:** страница загрузки + форма товара → этапы 0–7. Парсинг не нужен — самый короткий путь до работающих пинов.
3. **WB:** ссылка на карточку или выбор из магазина (`wb_store`) → отбор фото → тот же конвейер.
4. **Etsy** через официальный API (ключ у владельца есть; HTML Etsy закрыт DataDome, в 2.0 понадобились прокси и Selenium). **Ozon** — отдельная оценка, кода нет.

Каждый этап — отдельный PR с тестами (внешние вызовы через `unittest.mock.patch`).

## 6. Сменная модель

Сейчас `GigaChatProvider` создаётся напрямую в 9 местах. Для нового кода вводим два интерфейса:

- `TextModel.complete(messages, ...) -> Completion` (текст, токены, имя модели);
- `VisionModel.describe(image_bytes, prompt) -> Completion`.

Реализация выбирается настройками `STRATEGIST_TEXT_PROVIDER` и `STRATEGIST_VISION_PROVIDER` (по умолчанию `gigachat`). Новая настройка проходит по правилу четырёх мест из `AGENTS.md`. Смена модели = новый класс-реализация + значение настройки; конвейер, промпты и проверки не меняются. Старые 9 мест переводятся на интерфейс постепенно, отдельными изменениями.

Смена модели — решение владельца. Использование GigaChat API, включая платные вызовы, разрешено для выполнения задач.

## 7. Расходы на одну пачку

- Описание фото: 1 вызов VisionModel на новое фото (повторные — из кэша).
- Ключи: около 2 вызовов модели на товар в день (кэш 6 часов) + запросы Pinterest Trends.
- Текст: 1–2 вызова на пин.

Пример: 6 фото одного товара ≈ 6 + 2 + 6…12 = 14–20 вызовов.
