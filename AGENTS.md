# Правила совместной работы агентов · BoostKlient / курс Pinterest

Над проектом работают два агента: **Codex** (панель Codex в VS Code) и **Claude** (панель Claude Code).
Этот файл читают оба. У Claude в `CLAUDE.md` стоит ссылка `@AGENTS.md`.

У обоих агентов полный доступ к файлам. Пользователь его не ограничивает намеренно.
Значит, от порчи проекта защищает только дисциплина, описанная ниже. Её соблюдение обязательно.

## Роли

**Codex руководит и проверяет.** По новому прямому поручению пользователя 8 октября 2026 передаёт переделку всех15роликов Claude, контролирует соответствие сцен озвучке и сам просматривает итоговые MP4.

**Claude выполняет переделку.** Скрипты, захват в видимом браузере аккаунта Анны, монтаж, клипы, субтитры, комплекты площадок. Пользователь должен видеть окно браузера, реальные действия и момент захвата. Headless-захват запрещён. Новые версии отдельно; старые не перезаписывать. Никаких новых платных сервисов.

## Зоны владения

Большинство столкновений снимается тем, что у каждого файла есть один хозяин.
**В чужую зону можно только читать. Всегда. Без исключений.**
Нужно изменить файл в чужой зоне — пиши `ВОПРОС` в журнал и жди, либо бери замок (ниже).

| Зона | Хозяин |
| --- | --- |
| `docs/pinterest-course/*-сценарий.md` | Codex |
| `docs/pinterest-course/*-озвучка.txt` | Codex |
| `ПЛАН_ЗАПУСКА_КУРСА_PINTEREST.md` | Codex |
| `scripts/` | Claude |
| `artifacts/pinterest-course/visual-*/` — исходники визуала, скриншоты и их реестры | Claude |
| остальные файлы `artifacts/` | Claude |
| `video/` | Claude |
| `КУРС_PINTEREST/` | общая, только под замком |
| `AGENTS.md`, `ЖУРНАЛ.md` | общая, особый порядок |
| приложение BoostKlient (`apps/`, `templates/`, `config/`) | общая, только под замком |

## Замки на файлы

Папка `.locks/`. Один замок — один файл внутри неё. Агент создаёт и удаляет **только свои** замки,
поэтому при постановке замка мы не можем помешать друг другу.

Перед работой в общей зоне:

```bash
scripts/lock.sh list                  # посмотреть, что занято
scripts/lock.sh take <имя> claude "что делаю"
scripts/lock.sh free <имя> claude      # сразу после окончания
```

- `<имя>` — короткий слог задачи или пути, например `урок-09` или `КУРС_PINTEREST`.
- Если замок занят другим агентом — **не ждать и не снимать его**, взять другую задачу
  и записать в журнал, что было занято.
- Замок старше 6 часов считается забытым. Снять его можно, но обязательно записать это в ленту журнала.
- Замок не заменяет здравый смысл: он не защищает от двух правок, сделанных до его постановки.
  Поэтому сначала замок, потом чтение файла, потом правка.

## Журнал — канал связи

`ЖУРНАЛ.md` в корне. Единственный способ передать что-то другому агенту.
Пользователь не должен пересказывать нам слова друг друга.

- Перед началом работы агент **читает** журнал целиком.
- Журнал **только дописывается в конец ленты**. Чужие записи не редактируются и не удаляются.
  Так два агента не затрут друг друга, даже если пишут почти одновременно.
- Запись: дата, кто, что сделал или о чём спрашивает. Коротко, без воды.
- Вопрос помечается `ВОПРОС → Codex` или `ВОПРОС → Claude`. Ответ — отдельной записью.
- Раздел «Сейчас в работе» вверху правит только тот агент, чью строку он меняет.

## Порядок работы

1. Прочитать журнал.
2. Объявить задачу записью в ленту, чтобы второй агент видел, за что ты взялся.
3. Если задача трогает общую зону — взять замок.
4. Сделать коммит до начала крупной правки, чтобы откат занимал секунду.
5. Сделать работу, не выходя за свою зону.
6. Снять замок, дописать результат в ленту.

- Удалять или перезаписывать готовые материалы в `КУРС_PINTEREST/` без решения пользователя.
- Не трогать `.env`, ключи и учётные данные. Не выводить секреты в терминал, журнал или сообщения; токен хранить только в `/home/evgen/bk3.0/.local_secrets/youtube_token.json` с правами `600`; путь исключён из Git.
- Делать `git checkout`, `git reset --hard`, `git stash` и прочее, что сносит чужую незакоммиченную работу.
- Снимать чужой свежий замок.

## Правила по содержанию курса

- Только достоверное. Ничего не выдумывать: ни цифр, ни обещаний охвата, кликов и продаж.
- Скриншоты — реальные, с живого учебного аккаунта. Интерфейс не дорисовывать.
- **Каждый новый скриншот показывать пользователю до монтажа.** Файл и SHA256 — в `Версии_скриншотов.csv`.
- Анна — вымышленная героиня курса, это оговаривается в материалах.
- Не изображать результат, который фактически не проверен в Pinterest.
- Платные сервисы и API — только после подтверждения пользователя, с предупреждением о расходах.

## Прямая связь между агентами

Помимо журнала агенты могут спрашивать друг друга напрямую, без пользователя:

```bash
scripts/ask_codex.sh "вопрос или поручение"    # Claude → Codex
scripts/ask_claude.sh "вопрос или поручение"   # Codex → Claude
```

- Ответ приходит в stdout. Это новая сессия соседа: контекста его панели у неё нет, всё нужное пишите в вопросе.
- По умолчанию сосед работает только на чтение (Codex: `read-only`, Claude: `plan`). Для правок: `CODEX_SANDBOX=workspace-write` или `CLAUDE_PERMISSION=acceptEdits`. Зоны владения и замки действуют и здесь.
- Итог договорённости всё равно записывать в `ЖУРНАЛ.md`.

# Разработка приложения BOOSTKLIENT® 3.0

Django 5.2 модульный монолит для продавцов маркетплейсов: workspace → business → Pinterest-аккаунт → ИИ-стратег. Стек: Python 3.12, PostgreSQL 17, Valkey, Celery, GigaChat (Sber) как единственная LLM, серверные Django-шаблоны и рукописный CSS.

Подробности по подсистемам — в `AGENTS-DETAIL.md`.

## Роли агентов в разработке приложения

Решение владельца действует с 6 октября 2026:

- **Claude Code — главный агент.** Оценивает каждую задачу, решает, кто её выполнит, принимает результат и отвечает владельцу. Все решения по выполнению задачи принимает после проверки фактов и результатов, в пределах разрешённых действий и расходов. Обычные технические решения владельцу на согласование не возвращаются.
- **OpenCode — исполнитель ограниченных задач:** поиск, сбор фактов, черновики, механические правки. Использует бесплатные модели через OpenRouter и запускается через `.kilo/agent-state/run_opencode.py`. Результат принят только после проверки Claude.
- **Codex — генерация изображений (основная ниша) и отдельные поручения Claude или владельца.** Код и тексты по умолчанию не берёт, чтобы беречь недельный лимит. Без поручения не коммитит и не занимает файлы. Прямую задачу владельца выполняет, а коммит и занятые файлы согласует с Claude через `.kilo/agent-state/LOG.md`.

Перед каждой задачей прочитать `.kilo/agent-state/LOG.md`, `HANDOFF.md` и правила `.kilo/agent-state/DELEGATION.md`. Claude делегирует ограниченные работы, если передача контекста и приёмка дешевле самостоятельного выполнения. Не повторять полностью работу исполнителя; проверять результат и существенные изменения. Канал с OpenCode — только файлы, без HTTP-API. OpenRouter является провайдером моделей; прямые вызовы его API не входят в эту схему. Каждое поручение и итог фиксировать в журнале, учитывать качество, попытки и известные расходы при следующем выборе исполнителя.

### Когда Claude недоступен

Схема не должна приводить к тупику. Если Claude не запущен или исчерпал лимит:

- Codex или OpenCode сами принимают обычные технические решения и безопасные локальные изменения, в пределах правил репозитория, и записывают в `.kilo/agent-state/LOG.md` строку вида `<агент>: <решение>; причина: Claude недоступен; жду приёмки`.
- Решения владельца не заменяются: смена модели, `.env`, настроек, базы данных, удаление чужих изменений и расходы на другие сервисы или правка правил остаются за владельцем. Использование GigaChat API, включая платные вызовы, разрешено для выполнения задач без отдельного согласования каждого вызова.
- Приёмка откладывается, работа не отменяется: результат оформляется как обычно, но помечается «ожидает приёмки» и не считается закрытым до разбора Claude.
- Поручение, выданное Claude до остановки, исполняется по его букве и в срок, даже если приёмки пока не будет.

## Команды

Всё, что запускает Django, работает **внутри Docker**. Ни venv, ни глобально установленного Django.

    make up            # docker compose up --build
    make test          # docker compose exec web python manage.py test
    make check         # manage.py check
    make migrate       # manage.py migrate
    make makemigrations
    make shell
    make superuser
    make logs

`make clean` — это `docker compose down -v`, **удаляет локальную базу и медиа**.

Точечный тест (класс или метод, точечный путь):

    docker compose exec web python manage.py test apps.strategist.tests.StrategistChatTest --noinput
    docker compose exec web python manage.py test apps.pinterest -v 2 --noinput

Всегда передавайте `--noinput`: оставшаяся от прерванного прогона база `test_boostklient` заставит Django спросить подтверждение, и exec без TTY умрёт с `EOFError: EOF when reading a line` вместо запуска тестов. Тестам нужны запущенные PostgreSQL + Valkey, sqlite-фолбэка нет.

## Проверка

Линтера, форматтера и тайпчекера в репозитории **нет** — не добавляйте и не предполагайте ruff/black/mypy/pytest. Полное определение «проверено» — это то, что гоняет CI (`.github/workflows/ci.yml`):

    manage.py check
    manage.py makemigrations --check --dry-run
    manage.py migrate --noinput
    manage.py test

CI падает, если изменение модели приехало без миграции → коммитьте модель и миграцию одним изменением. Красный CI не игнорируется.

## Правило коммитов

Репозиторий общий, агентов несколько. Прежде чем что-то править или коммитить:

1. Прочитать `.kilo/agent-state/HANDOFF.md` и `.kilo/agent-state/LOG.md` — там видно, кто чем занят.
2. Задать имя **в окружении сессии**: `export AGENT_NAME="<имя>"`.
3. Занять файлы до правки: `.kilo/agent-state/agent.sh claim <имя> <путь> ...`. Второй агент получит отказ до того, как что-то испортит.
4. Коммитить по явным путям, не `git add -A`, и только занятые файлы.
5. После коммита: `agent.sh release <имя> <путь> ...`.

`git config agent.name` использовать **нельзя**: это один общий ключ на весь репозиторий, в нём помещается только одно имя. Второй агент, выполнивший эту команду, молча перезаписывает личность первого, и первый начинает получать отказ на собственных файлах. Это уже происходило в этом репозитории. Хук `.githooks/pre-commit` читает имя только из `AGENT_NAME`; если переменная не задана, он пропускает коммит лишь когда ни один файл в индексе не занят, а иначе отказывает.

Что нельзя, независимо от причины: коммитить в `main`, откатывать или удалять чужую работу, чинить чужое чужими руками без записи в `HANDOFF.md`. `--no-verify` — не способ обойти, а запись о том, что вы о чём-то договорились.

Защита двумя слоями: `.githooks/pre-commit` (локально, работает всегда) и защищённая ветка `main` на GitHub (PR плюс обязательное ревью плюс CI). Поэтому «запрос на подтверждение» для коммитов существует с обеих сторон.

## Соглашения, отличающиеся от дефолтов Django

- Пользовательский текст переводим (ru + en) и по-русски.
- Не сообщать владельцу usage, расход или стоимость GigaChat и не включать эти показатели в итоговые отчёты. Внутренние технические ограничения и защитные проверки сохраняются.
- Никакого `print()` в production-коде; никаких секретов, токенов и credentials в Git и логах.
- Ошибки fail closed: пользователю русское сообщение, в лог — детали, никогда трейсбек или сырая ошибка API.
- Основная ветка `main`, работа ведётся в `feature/*`.

## Переменные окружения

Settings читают только `os.getenv`; **в Python ничего не грузит `.env`**. Корневой `.env` потребляется интерполяцией Docker Compose, поэтому `manage.py` на хосте не видит ни одной переменной — используйте `docker compose exec`.

Новая настройка = правки в четырёх местах: `config/settings/base.py` (`os.getenv` с безопасным дефолтом) → `compose.yaml` (`x-app-environment`) → `compose.production.yaml` (`x-app-environment`, для секретов `${VAR:?required}`) → `.env.production.example`, если переменная нужна в продакшене.

Подводные камни: `PINTEREST_SCOPES` в settings по умолчанию включает `ads:read`, а оба compose-файла передают дефолт **без** `ads:read`. `production.py` не стартует без `DJANGO_SECRET_KEY` (≥50 символов), `DJANGO_ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS`. `PINTEREST_TOKEN_ENCRYPTION_KEY` должен быть валидным Fernet-ключом, и его нельзя ротировать без перешифровки сохранённых токенов.
